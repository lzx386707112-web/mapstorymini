## 2. 当前收尾的是哪一部分

本次最后收尾的是 **EventInstanceManager 的独立地图状态及接线**，主要解除怪物公园入口遇到的 `getInstanceMap/resetPQ` 缺口。没有把起源之塔整套玩法或所有副本算作本次完成项。

### 已实现的内容

1. 新增 `Assets/Scripts/Field/NativeEventMap.cs`。不同事件实例即使使用相同原地图 ID，也分别拥有怪物集合、刷怪调度、可变传送门、NPC 运行时列表、反应堆池和权威掉落池。
2. 脚本继续看到原地图 ID；内部用独立 `Scope` 区分状态。`FieldDirector.StateId` 供假人、反应堆、掉落桥等状态服务使用；`Map.id` 仍用于原地图/脚本语义，不能混用。
3. 每个实例重新读取原地图模型，避免动态 NPC 和传送门状态写入全局地图模板。
4. `resetPQ` 清理当前实例状态并按源端 `instanceMapFirstSpawn` 只立即生成 `mobTime == -1` 的一次性刷怪点；`instanceMapRespawn` 显式补怪。**没有让副本自动加入全局普通地图刷新。**
5. 玩家 `changeMap(mapHost, portalHost)` 可解析实际事件地图和目标传送门；切换时保存该实例存活怪物的 HP/位置，重新渲染时恢复。
6. 普通击杀、脚本清怪和友好怪回调区分 `hasKiller`；移除最后一只登记怪后再通知 `allMonstersDead`。脚本清怪防止 `ExpireNative` 和显式移除重复通知。
7. 事件 `setEventCleared` 与 `dispose` 分开：前者发原任务声望积分并延迟释放大厅名，不取消稍后到港/结束回调；后者释放地图状态。原角色字段 `fquest` 保存任务声望余数。
8. 事件奖励配置、实际发物品和退出时清理专属物品已接权威库存。补了实际声望增减，取代原 `getFame=0/gainFame` 空实现，声望按原端夹在 -30000～30000。
9. 更换角色、销毁宿主时清理实例地图；普通地图状态与副本状态保持分开。

### 已验证和没有验证的边界

已通过的定向回归包括：同一公园模板创建两个不同实例；两份怪物数量正确且独立；清理一份不清理另一份；传送门对象不共用；反应堆与地面掉落隔离；销毁后几何注册释放；事件末怪回调、无击杀者标志、通关后延迟回调仍执行；真实事件奖励入包、专属物品退出移除；声望上下限与任务积分商/余数持久化。

有边界的完整菜单审计已从 **688 条路径 / 31 条错误**降为 **688 条路径 / 2 条错误**；怪物公园 29 条独立地图入口报错已消除。两条剩余错误是 MTS 和起源之塔。路径通过只说明对应深度的脚本不再遇到那个宿主错误。

**仍未验证：Android 中实际打完六张公园地图、重复入场、死亡/掉线、所有币奖励、航海波次和整场结算。事件倒计时的原图 UI 仍未迁移。**

起源之塔的半成品专用移动/攻击拦截没有保留为已实现功能；交接时仍明确报缺失类，避免把未完成适配包装成挑战已修好。

## 3. 每项问题、下一步怎么改、怎么验收

### 1）进入游戏卡顿

**已经确定的原因之一**：宠物饥饿定时逻辑在库存根本未变化时仍重建整个 Profile 库存镜像，增加周期性工作。`NativeEquipmentEffects` 已改为实际变更后才刷新。此前已处理的选角重复写盘问题不能作为这次进图卡顿已解决的证据。

**尚未确定**：剩余卡顿来自地图/贴图读取、纸娃娃首次合成、声音加载、假人预热、事件初始化还是磁盘保存；没有本次 Android 的帧时间数据，不能直接指定某一个为唯一根因。

**下一步修改**：

1. 在同一 Android 设备记录选角到首个可控帧、首个可控帧后 10 秒、第二次进同图的帧时间；同时保留 `[Field/Enter]` 的 data/art/geometry/mobs/scripts 耗时。
2. 用已有帧日志/假人性能日志按时间对齐卡顿。检查 `FieldDirector`、`WzAssets/WzCharacter`、`AudioManager`、`BotPreload`、`NativeEventScripts`，只优化实际命中的热点。
3. 可分帧的准备工作按依赖拆分；Unity 贴图/对象创建留在主线程。不要把 Unity API 直接挪到后台线程，也不要仅通过延长黑屏掩盖进入后的停顿。
4. 对缓存首次建立与复用分别验证，不把“第二次不卡”当作冷启动修好。

**验收**：固定存档、地图、假人数和画质，至少做冷启动与热启动各 3 次；记录最大帧、P95/P99 和超过 100ms 的帧数。建议先以“首个可控帧之后不再出现明显冻结/连续输入丢失”为功能门槛，再确定设备对应的帧率目标；具体性能阈值需在设备基线上确认，不能冒称原端给定值。

**验收**：分别测试原按钮对应的各栏；成功只扣一次 2000、加 4；余额不足、满容量不扣款；反复点击不越上限；退出商城后可使用新格位；重启读回。仓库容量要验证同账户同世界共享、不同世界隔离。定向运输层已覆盖成功/不足/上限/账户世界行。

`NativeHuntTasks` 已按原配置、原发布周期和原 JS 接入。BOSS 击杀走真实金币/经验/点券/概率物品入口；任务共享、目标/非目标、重复不领奖、周期刷新有回归。

但是原收集任务 JS 扣材料后只调用 `markTaskCompleted` 并显示奖励；Java 的该方法明确只标记/广播，不发奖励。因此**原收集任务本身没有发显示的奖励**。没有擅自改原 JS 或补自造奖励。后续需要先决定是否修正源端规则，再执行明确授权的改动。

另需补狩猎胜利通用 `FIELD_EFFECT` 原图动画，并对经验增量、两种概率奖励以及满背包行为补定向断言；当前不能把胜利音效/文字等价于图片动画已接。

### 通用 FIELD_EFFECT 尚未渲染

已定位 EXE 字符串池 2500=`Map/Effect.img/%s`，候选分派函数 `0x5330F7`，图层函数 `0x534F92`，以及 `0x48BBA5` 的管理器原点对象读取。归档见 `docs/evidence/menu-feedback-2026-11-01/field-effect-*.txt`。

`0x534F92` 可见坐标参数 400/260、z=`0xC00614A4`、alpha255，以及动画和清理调用；**原点向量所属坐标系还没有证明，不能直接当 Unity 屏幕中心画出来**。需继续追管理器 `+0xDC` 的来源。原 `Map/Effect.img/quest/carnival/win` 有 21 帧，尺寸/origin/delay 不应重画或统一成自造时长。

### 数据库桥不是通用 JDBC

已接的六类查询用于本轮战力、排行和掉落等真实 SQL。其他语句仍严格报错。后续检查新菜单遇到查询必须对照原 SQL 实现真实读写，不要让任意 SQL 返回空表以“消除报错”。
