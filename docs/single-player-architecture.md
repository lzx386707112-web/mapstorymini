# 单机阶段的职责规划

本规划基于 2026-10-21 的代码。当前所有功能在 Unity 进程内运行，使用本地存档；不引入服务端、网络协议、数据库、依赖注入框架或通用事件总线。

后续已按原端源码开展第一轮实现；当前落地内容及未完成的一致性范围以 [原端玩法迁移记录](original-gameplay-port.md) 为准。下文保留最初规划供对照，不再作为最新代码现状。

本文描述目标边界及渐进改造顺序，**不代表下列模块已经实现**。现有脚本继续运行，后续开发按涉及的功能逐步收口，避免一次性重写。

## 1. 当前代码的实际情况

| 位置 | 现有职责与需要收口的边界 |
|---|---|
| `GameLoop` | 启动、场景构建、模式切换、刷怪数值、击杀奖励、存档、重开集中在一起；后续保留流程协调，逐步移出规则和对象构建细节 |
| `Profile` | 金币、职业、装备、装扮及 PlayerPrefs 读写混合；公开可写字段，装备方法还会自动授予所有权 |
| `Lobby` / `GameHUD` | 绘制、输入之外还调用存档；商店在 UI 内组合扣钱、授予和装备 |
| `PlayerCtrl` / `EnemyUnit` / `BossUnit` | 运动、战斗状态、伤害、动画、特效混合；普通怪与 Boss 分别实现暴击 |
| `SkillSystem` / `SkillDef` | 技能配置、剩余冷却、目标查询、效果计算、特效混合 |
| `HitFeel` | 震屏、闪白、顿帧之外，还承载暴击率、暴击倍率、击退等玩法参数 |
| `StageDirector` / `StageModel` | 已有关卡配置和运行流程分离的基础；流程仍直接访问 GameLoop 和表现，模型也包含 Unity 颜色与资源读取 |

已有本地存档、商店、装扮和平台移动；README 中早期 M0 的“没有存档”等说明不能作为当前架构现状。

## 2. 目标职责

| 职责 | 负责什么 | 不应负责什么 |
|---|---|---|
| 表现与输入 | UI、触摸/键盘、动画、音效、伤害数字、镜头、背景 | 决定价格、发放奖励、直接扣金币、读写存档 |
| 流程协调 | 启动、出战、返回大厅、重试、调用规则、安排保存、创建和销毁战斗对象 | 在流程中重复写伤害公式、装备合法性或价格规则 |
| 游戏规则与状态 | 金币与装备规则、伤害、技能冷却/Buff、奖励、关卡进度 | 操作 GameObject、Sprite、Resources、PlayerPrefs、播放特效 |
| 本地数据读写 | 读取配置、读写存档、版本迁移、缺省值与失败处理 | 判断购买资格、决定奖励多少、控制场景 |

调用方向：输入/UI → 流程入口 → 游戏规则；规则返回结果，流程安排保存和表现。数据读写由流程调用，规则只接收所需数据。简单公式可以直接调用普通 C# 方法，无须每次增加一层服务。

新提取的规则类优先使用普通 C#，显式接收时间增量、随机样本和数值；不依赖 Unity 生命周期。旧代码可暂时保留 UnityEngine，不能因此声称现有规则已经独立。

## 3. 状态的唯一归属

| 数据 | 唯一归属 | 生命周期 |
|---|---|---|
| 职业、已拥有武器、已装备武器、装扮、金币 | 玩家档案数据 | 跨局，写入存档 |
| HP、敌人、当前位置、冷却、Buff、当前段落、当局击杀数 | 战斗会话 | 出战创建，结束销毁；当前不做中途续战 |
| 武器价格/属性、职业技能、怪物属性、关卡奖励 | 只读配置 | 加载后只读，不能存放剩余冷却等运行状态 |
| 震屏偏移、闪白计时、动画播放进度、UI 选中项 | 表现对象 | 界面或对象存续期间 |
| 通关记录、经验/等级 | 将来对应的成长/进度数据 | 尚未实现，增加功能时定义持久化字段和迁移 |

出战时从档案和配置生成战斗初始属性；战斗期间不能每帧从 Profile 重算一份“第二套状态”。UI 读取状态或结果，不维护另一份金币、HP 或冷却。

## 4. 具体模块及入口约定

以下名称为建议，开发相应功能时再创建，不先建空类或空目录。

### 档案、商店与存档（第一优先级）

- `PlayerProfileData`：仅保存玩家数据，向 UI 提供只读访问；所有权与装备分开表达。
- `ProfileActions`：提供 `TryBuyAndEquipWeapon(id)`、`TryEquipWeapon(id)`、选择职业/装扮等明确入口。购买从配置取价，检查 ID、余额、是否拥有，成功后统一改变数据；失败不扣钱、不发物品。
- 装备入口检查已拥有；授予物品是另一项显式操作，不能沿用 `Profile.EquipWeapon` 自动授予的语义。已拥有物品再次点击购买不得重复扣款。
- `LocalProfileStore`：封装现有 PlayerPrefs 读写。先保持 `mxd.*` 键及默认值兼容，不为拆职责强行换格式。`Profile` 可暂时作为旧调用的兼容入口，逐个迁移调用点。
- 流程收到成功结果后保存，UI 根据结果显示成功或失败；存储失败必须可识别，不能宣称已经持久化。PlayerPrefs 无完整事务/备份保证。
- 金币变更统一校验范围，支出不得为负数，不能让 `Spend(-n)` 变成加钱。非法 ID 不使用目录的默认武器回退来完成购买。

增加多存档、复杂背包时，再采用带 `schemaVersion` 的文件存档，并实现旧 PlayerPrefs 迁移、临时文件替换与备份恢复；当前无需创建通用 Repository 接口。

### 战斗与技能（第二优先级）

- `DamageRules`：统一计算普通怪/Boss 的伤害、暴击及特殊倍率，返回伤害值和是否暴击。Boss 硬直期的 1.25 倍规则显式传入；不要在特效代码里算一次暴击。
- 生命状态先完成扣血和存活→死亡转换，再生成命中/死亡结果；重复命中已死亡单位不重复发奖。
- `SkillDefinition` 只放只读配置，`SkillRuntimeState` 放每个角色自己的剩余冷却与 Buff。施法入口检查有效角色、存活、战斗状态、攀爬限制和冷却，成功才消耗冷却。
- 目标搜索、碰撞和现有动作仍可留在 Unity 组件中；把目标数据交给规则计算，表现根据结果播放。先抽公式，不重写整个角色控制器。
- 暴击率、倍率、实际击退属于战斗配置；震屏幅度、闪白和动画属于表现配置。顿帧会暂停玩法时间，由流程统一协调暂停与恢复，避免效果脚本恢复时间时解除菜单暂停。
- 规则计算使用玩法时间；菜单/提示动画可用真实时间。现有无敌、关卡段落和技能使用的时间来源不同，迁移时先记录并保留行为，若统一时间语义须作为独立玩法变更验收。

### 关卡与奖励（第三优先级）

- `StageDirector` 先保留为 Unity 流程适配器；后续由 `StageSession` 持有当前关卡、段落、通关/失败状态，界面只读取。
- `RewardRules` 统一返回击杀、Boss、通关的奖励；流程负责应用到档案并保存。普通怪、Boss、关卡分别触发哪一种奖励要明确，不能同一奖励发两遍。
- 当前普通怪奖励为 5 金币、精英 15、Boss 80，击杀还有回血。保持现状，职责调整不顺带改经济数值。
- `StageModel` 已解析 `rewardExp/rewardGold`，但当前关卡通过流程没有发放这些配置奖励，也没有经验成长系统；接入必须单独实现并验收，不能把它写成已有能力。
- 新增通关奖励时，定义“每次通关”或“首次通关”的规则，用会话结算标记防重复；首次奖励还需持久化完成记录，奖励与记录一起保存。
- 战斗会话拥有本局的玩家、敌人、Boss、技能及段落任务；返回大厅/重开统一取消协程、清理引用和临时状态。重点核对当前 `EnterLobby` 未显式销毁 StageDirector 的路径。

### 运动、地图与资源

当前继续由 `PlayerCtrl`、`Art`、`Backdrop`、`CameraRig` 处理运动与显示。扩展时逐步把地形查询从角色静态字段收口到地图数据，把动画与输入从运动规则中分开；不在本轮改变移动手感或地图实现。

涉及 WZ、脚底锚点、相机、平台或绳梯的实际改造，必须先读取项目的 mapledash-map-port skill，遵守既有坐标约定并使用 MovementChecks 回归。

## 5. 新功能放在哪里

| 新功能 | 规则/状态 | 流程与表现 |
|---|---|---|
| 背包、装备属性 | 物品数据、容量、拥有与装备校验 | UI 发请求，成功后刷新并保存 |
| 经验、升级 | 成长数据、经验曲线、升级规则 | 击杀/通关调用，升级特效消费结果 |
| 任务 | 任务配置、进度、完成及领奖规则 | 战斗结果推动进度，任务面板只展示/请求领奖 |
| 掉落与拾取 | 掉落表、随机结果、拾取资格、背包变更 | Unity 生成掉落实体，拾取成功后移除表现 |
| 怪物技能 | AI/技能状态、命中及伤害规则 | MonoBehaviour 驱动更新，动画/预警消费结果 |
| 云存档或多人 | 重新设计同步、权威性、冲突处理 | 届时评估服务端；当前边界只减少耦合，不保证直接联网 |

## 6. 执行顺序与验收

每步单独改动、单独验收，不要求先搬动全部文件或增加 asmdef。未来提取出的代码可按 `Domain/`（规则/状态）、`Application/`（流程入口）、`Infrastructure/`（数据读写）归档，现有表现脚本逐步整理即可。

1. **先收口档案与商店**：提取数据、购买/装备规则和存储实现，迁移 Lobby 调用。验收旧档金币/装备不变；余额不足、负支出、无效 ID、未拥有装备、重复购买都不产生错误变更；成功购买与重启后数据一致。
2. **统一伤害规则**：普通怪/Boss 共用计算，先保持暴击与硬直倍率。用固定随机样本验证公式、死亡仅转换一次；在 Unity 验收数字、动画、击退与击杀奖励不变。
3. **拆技能配置与运行状态**：验证两个角色互不共享冷却、无效施法不消耗冷却，治疗/Buff/重开清理保持预期。
4. **收口会话生命周期和奖励**：出战→大厅→再次出战、死亡重试后没有旧 Boss/旧刷怪任务；每次死亡只奖一次。通关奖励/经验作为新增功能单独验收。
5. **随功能扩展存档与配置**：需要复杂背包/进度时再升级存档格式与迁移；怪物数值维护困难时再从 GameLoop 提取配置表。

对提取出的规则编写针对边界行为的测试；纯文档调整只核对引用和差异，不运行 Unity 构建。每次重构先保留行为基线，避免同时变更手感、经济和架构。
