# 假人系统性能基线 & 阶段1优化结果

> 目的：用可复现的离线压测回答「同图人多到底卡在哪」，并记录阶段1（零行为改动优化）的实际收益。
> 命令：`dotnet run --project tools/server-check -c Release`，输出 `[PERF]` 行。
> 环境：macOS / .NET 8 / Release。测的是 Server/ 纯 C# 层（模拟 + 调度 + 事件），**不含 Unity 渲染**。

---

## 一、结论：瓶颈不是每帧模拟，是「建卡」

| 场景 | 基线 | 阶段1后 | 变化 |
|---|---|---|---|
| 地形索引建卡 · 60 人（1203 foothold 图） | **204.8 ms** | **2.6 ms** | ↓ 79× |
| 地形索引建卡 · 120 人（同上） | **363.8 ms** | **0.02 ms** | 缓存命中 |
| 单次移动 tick 的对象分配 | 53.75 B | 0.02 B | ≈ 0 |
| 每帧遍历全服在册假人（1000 在线） | 0.008 ms | 0.000 ms | ↓ |
| 稳态每帧 · 60 人同图全在移动 | 0.21 / p95 1.05 ms | 0.21 / p95 1.0 ms | 持平 |
| 稳态每帧 · 120 人同图全在移动 | 0.26 / p95 1.73 ms | 0.30 / p95 1.5 ms | 持平 |
| 定时器 1000 个周期任务 · 每帧 | 0.002 ms | 0.002 ms | 未改（见 §五） |

读法：

1. **每帧模拟本来就不贵**。120 个假人同图全速跑，服务端每帧 0.3ms、p95 1.5ms。
   6000 元机 16.7ms 一帧里，这块占不到 10%。
2. **建卡才是那个「卡一下」**。1203 foothold 的图上，一个假人要 3.4ms，120 个就是 364ms。
   这笔钱花在「给每个假人各建一份完全相同的地形索引」上 —— 纯浪费。
   换算到游戏里：进一张有 120 个假人的图，`BotWorkPump` 的 4ms 预算会被这件事吃满 **90 帧**，
   表现为「进图后一两秒内人物动作发涩、掉帧」。
3. 顺带发现：`BotMovementPlayback` 每播一帧录制动作就 `new BotGroundIndex(map)`，
   出生编排（`portalenterdrop` / `turnaroundtoleft`）是逐帧播的，等于把建卡成本乘以帧数。

## 二、做了什么

| 改动 | 文件 | 说明 |
|---|---|---|
| 地形索引按地图共享 | `Bot/Environment/MapGeometry.cs`（新）+ 8 处调用点 | `BotGroundIndex` / `BotWalkRegions` / `BotAirCollision` 只依赖地图，改为每张图一份 |
| 缓存失效判据 | 同上 | 记录构建时的 `footholds.Count`/`ropes.Count`；地图被追加平台/绳索就重建 |
| 没消费者就不构包 | `BotMovementRuntime.Emit/EmitFlash`、`BotMovementService`、`BotRuntime` | 单机宿主没有网络出口，移动包原本「造完就扔」；现在没人订阅就跳过 |
| 游荡推进表 | `BotWander` | 只遍历真正在游荡的假人，不再每帧扫全服在册 |

### 为什么用 `ConditionalWeakTable` 而不是 mapId 字典

- 键是 **MapRuntime 实例**：同一张图重载后是新的实例，天然不会读到旧地形；
  测试里也存在「同 mapId、不同 foothold」的合成地图，用 mapId 会串味。
- 弱表在 MapRuntime 被回收时自动释放，不需要手工 Evict，也不会把地图对象钉在内存里。

### 一个被自检抓到的真实坑

`CheckMovement` 里有一段「先建图 → 再 `ropes.Add(...)` → 重建导航图」的用例。
只按实例缓存会让第二次构建读到**没有绳索的旧地形**，直接挂掉那条用例（549 → 548）。
因此缓存必须带形状指纹。这不是测试洁癖：任何「地图先注册、脚本后加绳索/平台」的路径都会踩到。

## 三、功能影响审计（逐项）

判定依据：这四项改动只碰「地形结构的构建方式 / 包的发送时机 / 遍历范围」，不碰任何算法与状态机。

| 功能 | 是否受影响 | 依据 |
|---|---|---|
| 市场假人（FM / 出售·收购商人 / NX / 扭蛋 / 社交） | 否 | 走 `BotMovementService` + `MarketBotDirector`，位置结果由地形决定；自检含市场三波生成、FM 说话/走动用例，全过 |
| 城镇游荡（TownWanderer） | 否 | 仍由 400ms 决策轮驱动；推进表只是「不再扫没有 wander 的假人」，`BotWander.Start/Stop` 语义未变 |
| 组队伴侣 grind（基友集合） | 否 | `BotPartyGrindFloors.Station` 换用共享地面索引，落点算法逐字未改 |
| 出生编排（掉落入场 / 转身） | 否 | 只把逐帧新建的地形索引换成共享；录制帧的播放顺序、`Apply` 对角色状态的写回都未改 |
| 移动 / 寻路 / 物理 / 传送门 | 否 | `BotGroundMotion`、`BotNavigationRuntime`、`BotTrajectory` 的算法一行未改 |
| 纸娃娃 / 外观 / 装饰器 | 否 | 未触碰 |
| 聊天 / 气泡 / 表情 / 卷轴特效 | 否 | `BotOutput` 未改 |
| 交易 | 否 | 未触碰 |
| 掉落 / 拾取 | 否 | `MapItemService` 未触碰；`DropCommands` 只用 `BotTasks`（未改） |
| NPC 对话 / 任务 / 传送脚本 | 否 | 未触碰 |
| 假人档案 / 等级职业分布 | 否 | 未触碰 |
| 观察者 gating（「没人看就不动」） | 否 | `IsObserved` 的注入与语义未改（阶段3 才会动它） |
| 视图渲染（`BotField`） | 否 | 视图读的是 `BotRegistry` 里角色的坐标/姿势，不读移动包；`Emit` 里 `SyncStance()` 仍在跳过构包之前执行 |

> 「移动包」这条链现在的接线是：**有人订阅 `BotRuntime.Movement` 才会接上下游**（自定义事件访问器）。
> 当前全工程无订阅者，所以是纯收益；将来真接联机时，订阅一下即自动恢复，不需要改别的。

自检：`server-check` **549 项全过**；`unity-compile-check` 0 warning 0 error。

## 四、阶段1 没做的事（以及为什么）

原方案里的「时间轮替换 `BotTasks.Drive`」，实测收益是 **0.002ms/帧**（1000 个周期任务）。
`FindAll` 扫 1000 项只要 2µs，把 200 行调度代码换掉、还要保住 fixedRate/fixedDelay/
嵌套调度/异常取消这些语义，风险收益比不划算 —— **暂不做，等真的出现「每帧几千个到期任务」再说**。

同理，「AOI 细化（阶段3）」在这组数字下也不是瓶颈：120 人同图全速跑，服务端只花 0.3ms/帧。
它的价值在**视图侧**（少建 GameObject、少合成纸娃娃），而视图侧的成本这次测不到（需要真机或编辑器里跑）。

## 五、下一步该测什么

服务端已经不像瓶颈了，剩下的开销在 Unity 侧，只有进游戏才量得到：

1. 打开 `debug_bot_perf=1`，跑一次「同图 120 假人」，读 `Bot/Frame` 日志的 P50/P95/P99。
2. 如果 `BotField.Create`（建视图 + 纸娃娃）占比高 → 做阶段4（View 池化 + 事件化）。
   进图批次已经改成按毫秒封顶（`BotField.MapEnterBudgetMs=6`）而不是按人头（原 `MaxCreateOnMapEnter=40`），
   所以慢机不会再被 39 个人头一次性撑爆；日志里会打出「没建完，剩 N 个分帧续建」。
3. 如果 `WzCharacter.Compose` 占比高 → 说明预合成没盖住实际动作集合，扩 `BotAppearancePrebake` 的动作范围。
4. 只有在 1~3 做完之后 P99 仍 > 4ms，才考虑阶段5（模拟移出主线程）。
